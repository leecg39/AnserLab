# 킹크랩 님이 말하는 흐름

1. 저장소를 GitHub에 연결합니다. ("일단 깃연결부터") 이슈와 PR을 쓰려면 원격 저장소가 있어야 합니다.
2. PRD를 2~3시간 공들여 작성합니다. 여기서 가장 중요한 기준은 Jake 님이 말한 "task끼리 같은 코드 영역이 겹치지 않게" 나누는 것입니다. 건드리는 파일과 폴더가 서로 다르면 병렬로 작업해도 충돌이 없고, 머지할 때도 쉽습니다.
3. Task 1은 직접 꼼꼼하게 시범을 보입니다. Task 1의 세부 항목을 빡세게 작성하고, 항목별로 PR을 하나씩 전부 올립니다. 이 과정이 AI에게 "이 주인은 이런 식으로 일하는구나"라는 본보기가 됩니다. (브랜치 이름, 커밋 단위, PR 크기와 본문 형식 등)
4. Task 2부터는 "워크플로우대로 해라"로 위임합니다. AI가 Task 1의 패턴을 따라 Task 2의 세부 항목 작성, 구현, PR 열기까지 스스로 진행합니다.
5. 중간에 떠오르는 수정 사항은 GitHub 이슈로 등록합니다. 작업 중인 흐름을 끊지 않고, 생각날 때마다 핸드폰 GitHub 앱으로 이슈를 남겨 두었다가 나중에 처리하게 합니다.
6. 세분화 자체도 AI에게 시킵니다. "task 세분화해, 우리 워크트리 최대한 이용해서 작업할 거야"라고 입력하면, git worktree로 병렬 작업이 가능한 단위로 나눠 준다는 뜻입니다. 워크트리는 한 저장소에서 브랜치별로 작업 폴더를 따로 두는 기능이라, 영역이 안 겹치는 task를 여러 에이전트가 동시에 진행할 수 있습니다.

## 요약

| 단계 | GitHub에서 하는 일 |
|---|---|
| 준비 | 저장소 연결 |
| 설계 | PRD 작성 (영역이 안 겹치게 task 분리) |
| 시범 | Task 1을 항목별 PR로 직접 올림 |
| 위임 | Task 2부터 같은 방식으로 AI가 PR 생성 |
| 보완 | 떠오르는 수정 사항은 이슈로 등록 |

"PRD 뼈대 → Task 1 → 워크플로우"가 킹크랩 님이 한 줄로 줄인 순서입니다.

## 참고 사항

- 대화 중 "워크플로우"가 정확히 무엇인지(문서로 적어 둔 작업 규칙인지, 특정 스킬인지)는 나오지 않습니다. 문맥상 Task 1에서 확립한 "task 작성 → 브랜치 → 구현 → PR" 절차를 가리키는 것으로 보입니다.
- 이 저장소에서는 그 절차를 [WORKFLOW.md](../WORKFLOW.md)로 적어 두었습니다.
